Magpie 的多账号号池插件：把一批 ChatGPT 普号批量导入本机，后台自动登录、自动同步成 Magpie
Providers，按剩余额度轮换、失败自动换号。**凭证只在本机处理，不上传任何地方。**

这一版给账号加上「哪天进来的」和「属于哪一批」，并让新批次在选号时占一点优势。

**升级后现有账号的分配完全不变** —— 老池子全是一个批次，加成对所有人乘同一个常数，
对轮转比例没有任何影响。批次权重只有在你有两个以上批次时才开始起作用。

## 装 / 升级

Magpie → 「插件」→「发现」→ 底部输入框填：

```
https://github.com/puaicg/magpie-gptpool
```

已经装过旧版的，推一下更新即可（`bun update magpie-gptpool` + 重启）。**账号库不动**
（`~/.magpie-gptfree/`），provider id 仍是 `gptfree-pool`，已保存的模型名继续可用。

## 为什么要加这个

买号是一批一批买的，不同批次的质量差别很大 —— 有的批次额度足、跑得很稳，有的批次
上游风控严、失败率高。但以前账号库里每条只有 `email/password/totp/accessToken/updatedAt`，
一次导入 37 个号就是 37 次独立写入，彼此没有任何关联。于是：

- 「这个号哪天进来的」—— 数据里不存在。
- 「这批号整体表现怎么样」—— 数据里也不存在。

`updatedAt` 帮不上忙：它每次刷新授权、重新登录都会被覆盖，那是「最近改动时间」。

## 新增了什么

**导入日期 + 批次**。每条账号现在带 `addedAt`（首次入库时间）和 `batchId`（批次号），
**首次写入即固定** —— 刷新授权、重新登录、重新导入同一个邮箱都不会改动它们。这两个
字段描述的是历史事实，不是当前状态；允许覆盖的话，一次重新导入就能把权重悄悄挪走。

一次导入 = 一个批次。批次元数据（标签、导入时间、条数、来源）单独存
`~/.magpie-gptfree/batches.json`，只放这些，**不含任何凭证**；账号本身仍然只存在
加密的 `pool.enc.json` 里。

**批次新鲜度权重**。第 0 新（最近一次导入）的批次 ×1.25，第 1 新 ×1.10，第 2 新 ×1.05，
更早的不加成。

倍数刻意压得很小，原因是批次权重和额度权重会**叠加**：新批次本来额度就更满，等于
同一个事实被算了两次。倍数一大就会把额度权重挤成配角，结果是把请求送进「批次新但
额度只剩 2」的号。1.25 的作用范围限制在「额度相近时把新批次排前面」。

只在**至少两个批次**时生效。`MAGPIE_GPTFREE_BATCH_RECENCY=0` 可整体关掉。

**面板**。账号列表在邮箱下面多一行「10-20 入库」，悬停能看到完整批次标签和第几批；
运行页新增「导入批次」区块，列出每个批次的号数、成功率、可用/限流/失效和剩余额度，
最新的批次排最前。成功率低于一半的批次会标红 —— 这就是「该不该继续给它权重」的
判断信号。

## 存量账号怎么办

0.10.x 之前导入的号没有批次信息，统一归到「历史批次」，导入时间显示「未知」。

**没有拿 `updatedAt` 回填**：那是「最近改动时间」，回填出来的是错的先后顺序，比空着
更糟。等这些号以后重新导入（先移除再导入）才会带上新批次。

## 升级注意

- 账号库、模型名、provider id 都不变，不用重新登录。
- 只有一个批次时批次权重不生效，所以升级当天的选号行为和 0.10.0 完全一样。
- 想验证效果：再导入一批新号，然后看运行页「导入批次」区块 —— 新批次的号会开始
  以约 53% : 47% 的比例（额度相近时）优先被派活。
