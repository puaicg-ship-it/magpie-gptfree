Magpie 的多账号号池插件：把一批 ChatGPT 普号批量导入本机，后台自动登录、自动同步成 Magpie
Providers，按剩余额度轮换、失败自动换号。**凭证只在本机处理，不上传任何地方。**

这一版**只加观测，不改调度**：升级后号的挑法、重试次数、预算全都和 0.9.0 一样，
只是侧边栏多了一个「运行」页，账本里多了几个字段。分级和权重是下一版的事 ——
先把「池子里到底发生了什么」看清楚，调参才有依据。

## 装 / 升级

Magpie → 「插件」→「发现」→ 底部输入框填：

```
https://github.com/puaicg/magpie-gptpool
```

已经装过旧版的，推一下更新即可（`bun update magpie-gptpool` + 重启）。**账号库不动**
（`~/.magpie-gptfree/`），provider id 仍是 `gptfree-pool`，已保存的模型名继续可用。

## 如果你还停在 0.8.16

这一版同时包含 **0.9.0 的破坏性改动**（0.9.0 只发到了我们的生产机，没有单独发过公开版本）：
号池在 Magpie 里从「一个号一条供应商记录」变成「整个池子一条」，Providers 页只会看到
一条「GPTFree号池 (N 个账号)」，老的 `gptfree-pool#s*` 记录第一次同步时会自动清掉。

模型名（`gptfree-pool/gpt-image-2`）不变，账号库不动，不用重新登录。这一改的目的是
把「用哪个号」的决定权从 Magpie 收回插件 —— Magpie 对我们这些号没有任何额度数据，
只能盲选，实测一次请求重试到 19 次、一次 7 分钟的成功其实是 8 次 × 55 秒。

## 新的「运行」页

面板从原来的「总览 / 图片 / 设置」变成「总览 / 运行 / 图片 / 设置」。运行页四块：

**六个指标卡** —— 可用账号、近 15 分钟成功率、P95 耗时（含首字 P95）、在飞请求数、
额度利用率、文本限流号数。以前这些数字要么没有，要么得去翻 `docker logs`。

**额度预警** —— 按「预计多久打空」排序。它比的是账本里新存的两个数：上次检测额度时
剩多少、现在剩多少，中间隔了多久。所以**它需要至少一次「检测额度」才会出现数据**，
刚导入的号不会有预测。一小时内要见底的标红。

**活跃账号 Top 20** —— 近 1 小时每个号打了多少次、成败比、平均耗时。哪个号在被
反复换掉、哪个号一直在赢，一眼能看出来。

**实时请求** —— 最近 150 条逐次记录，每 2 秒增量拉一次，切走或页面隐藏立刻停。
每行是一条**账号尝试**（不是一条用户请求）：时间、图片/文本、账号、结果、耗时、
详情（模型、张数、第几次尝试、HTTP 状态码、上游实际码）。

以前 `pool-stats.json` 只记聚合计数，`image-errors.jsonl` 只记失败 —— 于是「这次请求
试了哪些号、每个号多久、谁赢了」全都看不见，排查延迟和卡死时没有任何逐次线索。

> 这份日志在**内存**里，进程重启就清空（面板会写「本进程自 X 起」）。它默认不落盘：
> 每次请求都写文件会把 500 条裁剪的读放大搬到热路径上。要取证继续看「图片页 → 失败记录」。

## 修了什么

**面板打不开的问题**。这是本次唯一的线上故障修复。

现象：某天 01:23，另一个社区插件自动更新，触发 Magpie 插件宿主整体重启。旧的 GUI
服务还没释放 `127.0.0.1:37990`，新的重试 5 次后彻底放弃，而且没有任何自愈路径 ——
Magpie 的插件页代理只会去**连接**端口，不会重新调用插件入口。结果就是侧边栏面板
永久打不开，只能 `docker restart`。

现在前台重试失败后会挂一层后台守护继续尝试，端口一空出来服务自己就起来了。
日志做了节流，端口被别的进程长期占着时不会刷屏。

**文本限流的冷却重启就丢**。文本 429 的冷却原本只存在进程内的 `Map` 里，而宿主大约
每小时热更新一次 —— 冷却跟着没了，下一个请求又先去打那个正在限流的号。现在冷却
时间写进账本，重启后读回来继续生效。

顺带修了一个漏判：429 换号时原来只在错误码**恰好等于** `rate_limited` 才记冷却，
而上游实际返回的是 `rate_limit_exceeded`、`too_many_requests` 之类 —— 也就是说
绝大多数限流根本没被记下来。

**账号均耗时被系统性低估**。`Number(null)` 是 `0`，于是「没有历史值」被当成
「历史值是 0」，滑动平均从 0 起算：20 秒的首个样本会算成 6 秒。

## 顺手记下来的东西

上游每次返回的额度快照里，除了 `image_gen` 还有别的条目（`other_tool` 等）。以前
只抠 `image_gen` 那一项，其余直接丢弃 —— 那部分额度在账本里根本不存在。

这一版把**全量**存下来了（最多 12 条），但**没有据此做任何调度**：哪个条目算「文本
额度」是策略问题，得先看到真实数据长什么样再定。下一版会把非图片额度接进选号逻辑，
让「还有对话额度但画不了图」的号也能派上用场。

同时每个号开始记耗时画像（总耗时、首字耗时、样本数）。这一版只展示，不参与排序 ——
分级要用首字耗时而不是总耗时，因为总耗时几乎人人都能满足 45 秒，区分不出好坏。

## 升级注意

- 无需重装账号库，无需重新登录。
- 「运行」页的额度预警需要有「检测额度」的历史数据，新导入的号第一次检测后才会出现。
- 实时请求只在内存里，重启即空；要历史失败取证请看「图片页 → 失败记录」。
- `/api/health` 多了两个字段（`p95ImageMs`、`inflight`），判定 `ok` 的条件没变，
  已有的监控脚本不用改。
