Magpie 的多账号号池插件：把一批 ChatGPT 普号批量导入本机，后台自动登录、自动同步成 Magpie
Providers，按剩余额度轮换、失败自动换号。**凭证只在本机处理，不上传任何地方。**

这一版只做一件事：**同一个号同一时刻只让一个生图 worker 打。**

## 装 / 升级

Magpie → 「插件」→「发现」→ 底部输入框填：

```
https://github.com/puaicg/magpie-gptpool
```

已经装过旧版的，推一下更新即可（`bun update magpie-gptpool` + 重启）。**账号库不动**
（`~/.magpie-gptfree/`），provider id 仍是 `gptfree-pool`，已保存的模型名继续可用。

## 修的是什么

号池整体并发是 4。四个请求同时进来时，各自的**第一条 lane** 完全可能挑中同一个号 ——
那个号于是被四个 worker 同时打。上游看到的是突发流量，直接 429 或者干脆卡住。

权重排序挡不住这件事：降权只影响「谁排前面」，四条 lane 各自独立排序，第一名照样
是同一个号。请求内部的「已试过」集合也不行 —— 它只管同一个请求的两条 lane，
跨请求完全不管。

## 怎么做的

两层，缺一不可：

1. **领号时直接跳过在飞已满的号。** 第一轮扫一遍找空闲号；**全都在飞时挑最闲的那个
   硬上** —— 池子小的时候剔除等于不出图，宁可让一个号稍微超载也不能直接失败。
2. **在排序里把在飞已满的号降到 0.2 倍权重。** 只有硬跳过的话，排序还会把它们排前面，
   白白多扫一遍；只有降权的话，四条 lane 各自排序，第一名还是同一个。

计数在 `finally` 里减回来 —— worker 抛错、被客户端掐断、被预算掐断都要减。不减的话
一次异常就把这个号永久钉在「满」上，再也选不到。这条有单独的用例钉着。

## 配置

默认 **1**（同一时刻只让一个请求打这个号），面板「调度策略」里能改，`0` = 不限制。

想临时关掉不用改文件：

```
MAGPIE_GPTFREE_POLICY_PER_ACCOUNT_INFLIGHT=0
```

只作用于生图。文本请求很轻，同一时刻两个对话打一个号不会像生图那样把上游打爆。

## 会不会影响现在的分配

线上是 117 个号、并发 4 —— 这个闸几乎不会触发，它防的是「池子被用到只剩几个号」
那种时刻（那时四个请求抢两三个号，正是最容易把上游打爆的时候）。

池子里只有一个号时，并发请求仍然照常出图，不会因为这个闸直接失败。

## 测试

250 个用例。其中一条是**反证**：把闸关掉，同样的场景两个请求必然撞同一个号 ——
没有这条，主用例通过也可能只是碰巧。
