Magpie 的多账号号池插件：把一批 ChatGPT 普号批量导入本机，后台自动登录、自动同步成 Magpie
Providers，按剩余额度轮询、失败自动换号。**凭证只在本机处理，不上传任何地方。**

这一版修的是**文本（对话）链路**，不是生图：上游回 422 时不再是一句看不懂的
`{'detail': 'Invalid conversation body'}`，而且遇到「上游不认这个请求体」会自动换一种
发法再试一次。

## 装 / 升级

Magpie → 「插件」→「发现」→ 底部输入框填：

```
https://github.com/puaicg/magpie-gptpool
```

已经装过旧版的，推一下更新即可（`bun update magpie-gptpool` + 重启）。**账号库不动**
（`~/.magpie-gptfree/`），provider id 仍是 `gptfree-pool`，已保存的模型名继续可用。

## 修的是什么问题

有用户反馈：PI Agent 走号池对话时报 422，客户端只显示

```
magpie API error (422): {"message":"GPTFree号池: {'detail': 'Invalid conversation body'}"}
```

这句话两头都不好用：**看不出是谁拒的**（其实是 chatgpt.com 拒了我们构造的
conversation body），也**看不出我们发了什么**——那个单引号是 Python dict 的 repr，
我们的 worker 把上游响应体解析成 dict 之后又 `str()` 拼进了错误消息。

## 这一版改了什么

1. **错误文案说人话**。现在长这样：

   ```
   上游 422：{"detail": "Invalid conversation body"}（/f/conversation｜model=gpt-6-luna｜角色=user｜1 条消息｜已试：原始→system 折进 user→system 折进 user + 去 effort）
   ```

   上游原文用 JSON 表示（不再是 Python 的 repr）；后面是「哪一步、发的哪个模型、
   带了哪些角色、几条消息、试过哪几种形态」。下次再撞上，这句话本身就是线索。

2. **上游拒绝请求体时自动降级重试**。按「原始 → system 折进第一条 user 消息 →
   去掉 thinking_effort」的顺序试，只在上游回 400/422 时才降级，正常请求仍然一次就成，
   不会变慢。

   为什么先怀疑 system：ChatGPT Web 的 conversation body 只认 user / assistant。
   生图链路一直只发一条 user 消息，从来没撞上；文本链路却把客户端给的
   system / developer 原样搬进 `messages[].author.role`。agent 类客户端几乎一定带
   system prompt —— 合并进第一条 user 消息是这里最不坏的降级：语义还在
   （从「系统指令」变成「用户交代的前置说明」），但不会因为一个角色名把整单打死。

3. **`thinking_effort` 的重试条件修对了**。原来要求上游响应体里出现
   `thinking_effort` 这个词才重试，可它常常只回一句 `Invalid conversation body`，
   那个条件永远不成立 —— 等于没写。现在只要这一轮带了 effort，被 400/422 拒掉就
   重试一次不带。

4. **空响应体不再冒充生图错误**。文本链路拿不到上游 body 时，原来会被空值兜底
   写成 `Image generation failed`，现在留空、照常报状态码。

## 兼容性

- **生图链路一行没改**（`image_worker.py` 的 `UpstreamHTTPError` 签名都没动），
  只是文本链路在异常上多挂了一个 `hint`。
- 纯文本链路的改动，不动账本、不动凭证、不动接口。

## 还是报 422 怎么办

把新的那句错误原文发出来 —— 它已经写明是 `/f/conversation` 还是 prepare、发的哪个模型、
带了哪些角色、试过哪几种形态。剩下的就是照着缩：把 PI Agent 的实际请求体
（有没有 system、是不是多轮、带不带工具）贴上来即可。
