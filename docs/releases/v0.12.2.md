Magpie 的多账号号池插件：把一批 ChatGPT 普号批量导入本机，后台自动登录、自动同步成 Magpie
Providers，按剩余额度轮换、失败自动换号。**凭证只在本机处理，不上传任何地方。**

这一版修的是**出图链路上的三个真问题**：慢号拖死整单、一张图烧两份额度、客户端干等
26 秒后放弃。

## 装 / 升级

Magpie → 「插件」→「发现」→ 底部输入框填：

```
https://github.com/puaicg/magpie-gptpool
```

已经装过旧版的，推一下更新即可（`bun update magpie-gptpool` + 重启）。**账号库不动**
（`~/.magpie-gptfree/`），provider id 仍是 `gptfree-pool`，已保存的模型名继续可用。

## 一、慢号不再拖死整单

线上 12 次尝试里，`gpt-image-2.6` 有 8 次卡在 **55.0 秒整** —— 但这 8 次的**首字节
都在 2.7–5.0 秒**。首字节来了就说明上游在推流，**是慢不是卡死**。

| | 原来 | 现在 |
| --- | --- | --- |
| 单账号上限 | 55 秒（2.6 是 75 秒） | **60 秒，所有模型统一** |
| 整单上限 | 150 秒 | **10 分钟** |
| 主要退出条件 | 超时 | **号试完了** |

60 秒的依据：成功样本集中在 21–38 秒，**超过 60 秒的一次都没成功过**。号池里有两百
多个号，等一个慢号的机会成本比换一个号试更大。

原来的组合（单次 75 秒 + 整单 150 秒）意味着一个请求只够试 **2 个号**，然后就报
「所有账号都失败」—— 池子里还有两百个号从没被用过。现在整单只在天花板或号试完时
才收手。

真卡死的号处理得更早：**10 秒没首字节就直接换**，不用等满 60 秒。

## 二、不再一张图烧两份额度

两个独立原因，都修了。

**对冲在复制一个本来会成功的请求。** 老规则是「头号 30 秒还没结果就再起一路去别的
号上重试」，而 2.6 的正常耗时 21–37 秒**跨越了这条线**。于是本来会成功的请求在
30 秒被复制，第一路 35 秒赢了、第二路被掐断 —— 但上游那边已经在生成。

现在**首字节来了就不对冲**。探索路（专门去试没上过场的号）单独留了开关
`exploreWhileProgressing`，默认关 —— 打开它会换回探索能力，代价是慢请求会多生成一份。

## 三、客户端不再干等 26 秒后放弃

出图要 20–40 秒，这期间我们以前一个字节都不发，客户端把长连接当成死连接、26 秒左右
就放弃 —— 响应到达时它已经不看了。

更糟的是上一版只发了 `: keepalive` 注释帧，而**客户端解析 SSE 等的是 `data:` 帧**，
注释帧等于没数据。于是它 5 秒左右就**重发了一次请求** —— 一次点击生成两张图、
烧两份额度。

现在：

```
客户端发 1 个请求
  → 41ms 收到 role 帧（知道模型开始回复了）
  → 每 5 秒一条 keepalive（连接不会被认为死了）
  → 号 A 试 60 秒没出图 → 换号 B → …
  → 出图 → 同一个 id 发内容 + stop + [DONE]
```

## 四、「超时」拆成了两种

以前 `worker_timeout` 混了两件事，后果是**慢模型会把池子里的好号一个个隔离掉**：

| 错误码 | 含义 | 怎么处理 |
| --- | --- | --- |
| `worker_hang` | 10 秒内一个字节都没来 | 真卡死，记进 `hangStreak`（2 次隔离 30 分钟） |
| `worker_slow` | 首字节来了，只是没在预算内出图 | 模型慢，只记普通失败 |
| `attempt_aborted` | 我们主动不等了 | 新码，以前完全不可见 |

## 配置

| 键 / 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `policy.imageAttemptTimeoutMs` | 60000 | 单账号上限 |
| `policy.imageSlowModels` | `{}` | 给某个模型单独放宽，如 `{"gpt-image-2.6": 75000}` |
| `policy.exploreWhileProgressing` | false | 头号在推流时还要不要起探索路 |
| `MAGPIE_GPTFREE_MAX_TOTAL_MS` | 600000 | 整单天花板 |
| `MAGPIE_GPTFREE_SSE_KEEPALIVE_MS` | 5000 | keepalive 间隔 |

## 升级注意

- **一次请求现在最长可以占 10 分钟并发**（号池并发上限是 4）。四个都卡住会把号池
  堵死 —— 这只会在整池都不健康时发生，那时本来也出不了图。彻底解决要靠「按错误族
  提前熔断」，那是后面单独一个版本。
- 单次上限从 55/75 秒统一成 60 秒，**2.6 比上一版收紧了一点**。想放宽就填
  `imageSlowModels`。
- 非流式请求行为没变。

## 测试

260 个 JS 用例 + 24 个 Python 用例。新增覆盖：首帧必须是 data 帧、生成期间持续
keepalive、流式失败回 error 帧、首字节后不对冲、探索开关、`worker_slow` 不记卡死、
`attempt_aborted` 留痕、60 秒预算解析。
